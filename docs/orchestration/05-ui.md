# 05. UI 구현 계약

[명세 입구](../../ORCHESTRATION_SPEC.md)

용어: 사용자 문구는 mission=**AI 작업**, task=**할 일**, run=**실행**, candidate=**결과**, accept=**확정**, Decision=**결정 필요**를 쓴다. 문자열 정본은 `src/i18n/sections/missions.ts`다. 사용자 안내는 [AI 작업 사용법](USER_GUIDE_KR.md)과 [상세 안내](USER_GUIDE_DETAILS_KR.md)에 있다.

## 1. 기본 레이아웃

O1의 기본은 **AI 작업당 탭 하나, 왼쪽 Lead 대화, 오른쪽 할 일 목록과 그 아래 실행 상세 또는 결과**다. 새 agent/run 생성 시 자동 탭 생성/포커스 이동/분할 추가 금지. 기존 일반 terminal 탭은 같은 상단 바에서 유지한다.

```text
[터미널] [로그인 기능 · 결정 필요 1] [성능 개선 · 확정 대기] [+]   [+ 새 AI 작업] [☰]
로그인 기능  실행 중 · 구현 중 · 활성 시간 12분 / 24시간        [실행 제어 ▾]
[결정 필요 1: 계획 확인 필요                                   열기]
┌───────────────────────────────┬───────────────────────────────┐
│ Lead 대화                     │ 할 일  실행 2 · 완료 1 · 결정 1│
│ 사용자 목표                   │ [전체][실행 중][응답 필요]…[검색]│
│ ▸ 채택된 계획 · 할 일 3개      │ ▶ API 구현 · gpt-5.6-luna      │
│ 진행 보고 / 결정: 계획 적용    │ ▶ UI 구현 · gpt-5.6-luna       │
│                               │ ◷ 통합 · 선행 할 일 대기       │
│                               ├───────────────────────────────┤
│                               │ [실행 상세] [결과 •]           │
│                               │ API 구현 · 실행 중             │
│                               │ [활동] [변경] [검증]           │
├───────────────────────────────┤                               │
│ AI 작업 전체에 요청…          │ [이 할 일에 추가 지시]         │
└───────────────────────────────┴───────────────────────────────┘
```

Lead와 오른쪽은 독립 scroll container다. AI 작업 header, 결정 배너, composer는 해당 pane에 고정하고 body 전체가 terminal 입력 때문에 scroll되지 않는다.

**Header**는 제목, AI 작업 상태, 단계, `활성 시간 {사용} / {한도}`(tooltip: 활성 시간 정의)와 `실행 제어 ▾`다. 메뉴는 `새 실행 일시정지`(running) / `계속 실행`(paused) / `AI 작업 중단` / `AI 작업 한도…`이며, 일시정지·중단이 끝나기를 기다리는 동안(pausing/stopping)은 제어 대신 `종료 확인 대기 중인 실행 N개`와 `첫 실행 상세 열기`(종료 증거가 없는 실행을 먼저 연다)를 보인다. 끝난 AI 작업은 메뉴를 비활성화하고(`끝난 AI 작업은 제어할 수 없습니다.`) `보관` 버튼을 보인다. 초안은 `시작`과 `초안 삭제`(중단→보관, 확인창)를 보인다. 시작이 `base_changed`/`repository_changed`로 거절되면 오류 아래에 `같은 목표로 새 AI 작업`을 둔다.

**결정 배너**는 열린 결정이 있을 때 `결정 필요 {N}: {종류별 짧은 제목}`과 `열기`/`접기`다. 제목은 질문 원문(JSON일 수 있음) 대신 종류별 문구다: 파일 변경 허용, 통합 충돌, 리뷰 수정 한도, 결과 불명 실행, 실패한 할 일, 비용, 그 밖은 `질문에 답변 필요`/`승인 요청`/`한도 확인 필요`/`복구 방법 선택 필요`/`계획 확인 필요`/`충돌 해결 방법 선택 필요`. 배너는 결정 패널을 이 페이지 안에서 연다(강제 탭 전환 없음). 답하면 다음 열린 결정으로 넘어가고, 없으면 패널을 닫고 `답변을 저장했습니다`를 4초 보인다. `aria-live="polite"` 영역은 결정이 없을 때도 자리를 지키는 배너 한 곳뿐이다. 끊김이면 `열기`를 막고 `연결이 복구되면 답변할 수 있습니다.`를 tooltip으로 둔다.

**오른쪽 아래 영역**은 `실행 상세`와 `결과` 토글이다. 사용자가 고른 적이 없으면 단계 기본값(확정 대기 또는 완료면 결과, 아니면 상세)을 쓴다. 단계가 `awaiting_acceptance`로 **바뀌는 순간 한 번** 사용자 선택을 비워 결과를 보이고(좁은 폭은 결과 탭으로 이동), 그 뒤 사용자가 고른 영역을 존중한다. 확정 대기 중에는 결과 토글과 좁은 폭 결과 탭에 점(`확정 대기` 낭독용 숨김 문구)을 붙인다. 선택한 할 일이 없으면 자동으로 실행 중인 Lead, 없으면 첫 실행 중·응답 대기 할 일을 고른다(사용자 선택을 덮지 않는다).

**연결 상태**는 전송 계층(`transportStatus`, 3초 주기)과 동기화 오류를 구분한다: 끊김 > 기록 없음 > 일시 지연 > 실패 순으로 하나만 보인다(§10).

## 2. 탭 타입과 저장

TabState는 아래 union이다. kind가 없는 v1 데이터는 terminal로 migration한다.

```typescript
type TabState =
  | { kind: 'terminal'; id: string; title: string; root: SplitNode | null }
  | { kind: 'mission'; id: string; title: string; missionId: string }
  | { kind: 'agent-view'; id: string; title: string; missionId: string; taskId: string };
```

root 접근 전 kind guard가 필수다. LiveTabItem, close all, native menu, command palette, focused leaf, split shortcut, quit dialog, pane 이동·합치기·재그룹을 모두 점검한다. AI 작업 탭에 가짜 PTY/leaf를 만들지 않는다. 탭 이름 편집은 terminal 탭 전용이며 AI 작업 탭 제목은 missionStore 제목 → 저장된 탭 제목 → `AI 작업` 순서의 폴백이다. agent-view 탭은 같은 할 일의 RunDetail을 보는 별도 보기(새 실행 아님)로 저장·복원되며, 현재 화면에는 여는 버튼이 없다. 기록이나 할 일이 사라지면 무한 로딩 대신 탭 닫기를 권한다.

`missionUiStore`는 AI 작업별 selectedTaskId/selectedRunId/selectedByUser/detailTab/filter/search/leadWidthRatio/teamListHeightRatio/narrowView/sheetOpen/rightPane/observedPhase를 메모리에만 둔다(persist 없음). 실행 상태와 대화 원문은 저장하지 않는다. 닫아서 숨긴 AI 작업 id는 workbenchStore `hiddenMissions`다. `missionStore`는 daemon snapshot의 normalized map, atSeq/revision/loading/error/dirty를 관리한다.

workspace v2 key는 `iyagi.workspace.v2`. read 순서는 v2→유효한 v1→빈 상태다. v1 migration에서 terminal ID/ratio/viewId를 보존한다. v2 write 성공 후에도 v1을 자동 삭제하지 않는다. malformed v2 entry는 해당 탭만 격리하고 다른 탭을 복원한다. 전체 512,000 bytes 한도 유지. daemon에 AI 작업이 없으면 `AI 작업 기록을 찾을 수 없습니다`, `이 탭이 가리키는 AI 작업 기록이 데몬에 없습니다…`와 `탭 닫기`만 제공하며 자동 재실행하지 않는다.

AI 작업 계열 탭(mission + agent-view)은 최대 16개다. 초과 시 AI 작업 생성·실행을 취소하지 않고 안내만 한다: 새 AI 작업 대화상자는 `AI 작업을 만들었습니다. AI 작업 탭이 이미 16개라…` 토스트, 작업 목록은 대화상자 안의 `role=alert` 안내(토스트로 덮지 않음). 동일 AI 작업은 한 창에서 탭 하나만 열고 기존 탭으로 이동한다. agent-view는 task ID로 중복 검사한다. 일반 terminal pane/session cap은 별개다.

### AI 작업 목록

상단 막대의 `☰`(새 AI 작업 버튼 옆), 메뉴 막대 `AI 작업 목록…`, 명령 팔레트 `AI 작업: 목록…`이 modal `mission-list`를 연다. 탭을 닫아도 AI 작업은 데몬에서 계속 실행되므로 이 목록이 다시 여는 자리다.

- 열 때 `mission.list`(보관 제외)를 모두 읽어 **결정 필요**(끝나지 않았고 열린 결정 > 0) / **확정 대기**(`awaiting_acceptance`) / **진행 중** / **끝남**(completed·failed·cancelled, 남은 결정 수와 무관)으로 묶는다. **보관됨**은 그 필터를 고를 때만 `archived: true`로 따로 읽는다. 필터 칩은 전체·결정 필요·확정 대기·진행 중·끝남·보관됨과 개수이며, 결정 필요가 있으면 강조한다.
- 행: 제목 · 저장소 이름(경로 tooltip) · 상태·단계 · `결정 N`(끝나지 않은 경우) · `탭 열림` · `갱신 {시각}`(오늘 HH:MM, 올해 MM-DD HH:MM, 그 밖 YYYY-MM-DD HH:MM). 정렬은 updated_at 내림차순. 검색은 제목·저장소 경로·저장소 이름.
- 행을 누르면 탭을 열고(이미 열려 있으면 이동) 대화상자를 닫는다. 보관됨 행은 `보관 해제`(`mission.control(unarchive)`). 끝남·보관됨 행에는 작업 공간 정리(§9)를 붙인다. 머리에는 `AI 작업 공간 {size}` 전체 사용량(조회 실패는 숨김)과 `새 AI 작업`.
- 아무 AI 작업도 없으면 빈 상태 `아직 AI 작업이 없습니다` + 설명 + `새 AI 작업`. 조건에 맞는 것이 없으면 `조건에 맞는 AI 작업이 없습니다.`. 읽은 요약은 missionStore에 넣어 열린 탭의 제목·배지도 채운다.

### 탭 배지와 알림

AI 작업 탭 배지는 상태 우선으로 하나만 보인다: `결정 필요 N` > `확정 대기` > `실패` > `실행 중 N` > `완료`. 끝난 AI 작업은 남은 결정·확정 대기를 배지로 보이지 않는다. snapshot을 뽑은 탭은 snapshot의 열린 결정 수·live Run 수를, 뽑지 않은 백그라운드 탭은 `mission.list` 요약(open_decision_count·state·phase)을 쓴다(live Run 수를 모르면 `실행 중`만). selector는 원시 문자열로 인코딩해 다른 갱신이 탭 렌더를 반복시키지 않는다. 배지가 결정 필요로 **바뀔 때만**, 보고 있지 않은 탭이면 `AI 작업 ‘{title}’에 결정이 필요합니다.`를 앱의 polite 토스트로 한 번 알린다(앱 시작 시 처음 채워지는 배지는 알리지 않는다).

알림 센터는 missionStore 변화 중 사용자의 손이 필요한 전이만 한 줄씩 남긴다: 새 결정(`AI 작업 결정 필요`, 상세 `결정이 필요합니다`), 확정 대기 진입(`AI 작업 확정 대기`), 실패(`AI 작업 실패`). 앱을 켜기 전부터 있던 상태는 기준선만 잡고, 켠 뒤 만들어진 AI 작업은 처음 볼 때도 알린다. 같은 사건은 id(AI 작업 id + 사건 + 결정 id 또는 revision)로 한 번만 남긴다. 사용자가 그 AI 작업 탭을 보고 있으면 남기지 않는다. 데스크톱 알림은 기존 게이트(창이 숨겨져 있고 권한이 있을 때)로 결정·확정 대기에만 보낸다.

### 닫기 안내와 보관 되돌리기

AI 작업 탭 닫기는 로컬 숨김이다(종료 확인·취소 요청 없음). 닫으면 토스트로 알린다: 끝나지 않았으면 `AI 작업은 계속 실행됩니다 · AI 작업 목록에서 다시 열 수 있습니다.`, 끝났으면 `AI 작업 탭을 닫았습니다 · AI 작업 목록에서 다시 열 수 있습니다.`.

보관(header `보관`, 결과 화면 `이 결과 버리기`, `초안 삭제`)은 탭을 닫으므로 페이지 밖에 자기 root를 가진 토스트 `보관했습니다 · 되돌리기 · ×`를 8초 띄운다(한 번에 하나, 누르면 자동으로 사라지지 않음). `되돌리기`는 `mission.control(unarchive)` 후 탭을 다시 연다. 보관한 AI 작업의 작업 공간을 정리할 수 있으면 `작업 공간 {size}는 AI 작업 목록의 보관됨에서 정리할 수 있습니다.`와 `목록 열기`만 덧붙인다(별도 팝업 없음, 조회 실패는 숨김).

## 3. 새 AI 작업

탭 막대의 `+`는 누르는 즉시 새 터미널 탭을 연다. 새 AI 작업은 상단 막대의 `+ 새 AI 작업` 버튼(새 터미널 버튼 옆, 옆에 `☰` 목록 버튼)과 명령 팔레트 `AI 작업: 새로 만들기…`, 메뉴 막대 `새 AI 작업…`, 단축키 `Cmd/Ctrl+Shift+M`(사용자 설정 가능, 기존 shortcut과 충돌 검사), terminal pane 오른쪽 클릭 메뉴 `이 폴더에서 AI 작업…`(cwd가 없으면 숨김), 에이전트가 떠 있는 pane ⋯ 메뉴 `이 저장소에서 AI 팀에 맡기기…`(tooltip: 현재 대화는 옮겨지지 않음)에서 연다. 모든 진입점은 초점 pane의 `project ?? cwd`를 저장소 초기값으로 넘기고 같은 가용성 판정을 쓴다: daemon이 `mission_protocol`을 선언하지 않으면 개발 빌드는 비활성 + `AI 작업은 개발 빌드에서만 켤 수 있는 미리보기 기능입니다.`, 프로덕션 빌드는 숨김. daemon 프로토콜이 앱보다 새로우면 비활성 + `데몬의 AI 작업 프로토콜이 이 앱보다 새롭습니다. 앱을 업데이트하세요.`.

처음 보이는 것은 제목·부제, 저장소, 목표, 팀, 리뷰 방식이다. 완료 조건과 실행 설정은 접는다. 보존 안내와 사용법(MissionGuide)은 맨 아래다.

| 필드 | 초기값/검증 |
|---|---|
| 저장소 | 진입점이 넘긴 projectRoot/cwd. 초기값이 있으면 열 때, 입력을 바꾸고 벗어나면 자동 inspect(마지막 확인만 반영). 결과는 canonical path · HEAD 12자 · `작업 트리 깨끗함`. dirty면 경고 + 변경 경로 최대 20개 + `외 N개` + untracked 안내와 함께 `커밋하지 않은 변경을 포함해서 시작` 선택을 기본 켜짐으로 보인다(후속 작업이면 숨김). 켠 채 제출하면 `include_uncommitted`를 보내 그 작업 트리가 base가 되고, 끄면 오늘처럼 `Git 변경이 남아 있습니다…`로 막는다. start 시 daemon이 기록한 HEAD·작업 트리를 다시 검사한다 |
| 목표 | multiline, 빈 값 금지, 최대 256 KiB UTF-8(90% 이상이면 바이트 표시). 제목은 첫 줄 48자 |
| 팀 | 선택이 없을 때만 첫 template 자동 선택(refresh가 사용자 선택을 바꾸지 않음). 역할별 모델 연결을 `binding.list`로 점검하며, 없는/미검증 역할은 `{role} 역할에 필요한 자동 실행 지원이 확인되지 않았습니다…` + `설정 열기`. template이 없거나 역할이 모자라면 빠른 설정 카드를 대화상자 안에 붙인다. 연결 목록 조회 실패는 이유 + `다시 시도` |
| 리뷰 | 접지 않는 라디오: `리뷰 포함(권장)` / `리뷰 생략(빠름) — 독립 리뷰 없이 검증 명령과 직접 확인으로 확정합니다`. 기본은 팀을 따른다(reviewer 연결과 독립 리뷰 정책이 모두 있어야 포함) |
| 완료 조건 | 선택 사항, 기본 접힘. requirement 목록, 등록된 검증 command ID, human check. 비우면 `목표 달성 확인: <목표 첫 줄 200자>` human check 조건 하나를 만들어 daemon의 최소 1개 규칙을 지킨다 |
| 실행 설정 | 기본 접힘, summary `병렬 {n} · 시도 {n} · {분}분 · {비용 상한}`. 병렬도(1–4), 할 일당 최대 시도, 실행 시간 제한(분 입력, ms 저장, 1..ceiling), 비용 상한(USD, 소수 6자리), 미확인 비용 처리, 네트워크 허용, 계획 자동 적용 |
| 보존 안내 | 로컬 저장하는 내용과 닫기·보관의 의미 |

**빠른 모드(리뷰 생략)** 는 `policyWithReviewMode`로 독립 리뷰 요구를 끄고 reviewer를 역할 연결·허용 역할에서 빼며, 필수 역할을 lead·builder로 준다. 리뷰 포함이면 필수 역할은 lead·builder·reviewer이고, 팀에 reviewer 연결이 없으면 역할 부족으로 막는다(daemon start의 `builder_missing`·`reviewer_missing` 검사와 같다). integrator는 두 방식 모두 선택 역할이다 — 팀에 있으면 자동 실행 기능만 검사하고, 없으면 막지 않고 팀 영역에 `충돌 해결 담당(Integrator)이 없으면 충돌 시 변경을 제외하고 다시 계획하는 방법만 쓸 수 있습니다` 한 줄을 보인다(통합 충돌 결정에 `Integrator에게 해결 요청` 선택지가 없다). 역할 부족 안내의 역할 이름은 slug가 아니라 사람 문구(`Builder · 구현` 등)다.

**실험적 연결 표시**: 필수 역할이 모두 준비됐고 그중 하나라도 실험적 연결(검증되지 않은 CLI 버전을 동의하에 사용)이면 팀 아래에 `실험적 연결 포함 — …결과에 표시가 남습니다.`를 보인다. 생성은 막지 않는다.

**검증 지원 OS**: 저장소 확인 결과 `verification_supported: false`면 완료 조건 안에 `이 OS에서는 검증 명령 자동 실행을 아직 지원하지 않습니다 — 사용자 확인으로 대체하세요.`를 보이고 검증 선택을 비활성화하며, 그 저장소를 처음 확인할 때 기존 조건을 사용자 확인으로 바꾼다(새로 추가하는 조건도 사용자 확인 기본). 제출 시 검증 ID를 보내지 않는다.

**후속 작업 base**(`followUpOf`): 이전 AI 작업을 store에서 읽고 없으면 동기화 기록을 남기지 않는 한 번 읽기(`peekMission` — Mission·Candidate만)로 채운다(탭 없는 이전 작업이 이후 힌트마다 전체 재동기화 대상이 되지 않게). 확인 중에는 `이전 결과를 확인하는 중…`으로 제출을 막는다. 이전 AI 작업이 completed + accepted_at + 그 candidate가 있으면 `이전 확정 결과 위에서 시작 · 커밋 {7자}`를 보이고, 확인한 저장소가 같은 저장소(repository_id 또는 canonical path)일 때 `expected_base_oid = 결과 커밋`, `follow_up_of`를 보낸다. 이때 HEAD·dirty 경고는 숨기고 clean 검사를 하지 않는다(판단은 daemon). 후속 작업이 아니면 `follow_up_of` 키 자체를 보내지 않는다(구 daemon의 `MissionCreateParams`는 모르는 필드를 거절한다). 저장소가 다르면 `이전 AI 작업과 다른 저장소라 현재 HEAD에서 시작합니다.`, 확정되지 않았으면 `이전 AI 작업이 확정되지 않아 현재 HEAD에서 시작합니다.`. 목표 초기값은 `이전 AI 작업 ‘{title}’의 결과를 이어서:` + 원래 목표 인용이다(같은 목표로 새 AI 작업은 원래 목표 그대로).

**흐름과 중복 생성 방지**: goal artifact upload → `mission.create` → `mission.control(start)`. 제출 중 입력·버튼 disabled. create 성공 후 start 실패는 오류(`AI 작업은 만들었지만 시작하지 못했습니다.` + 원인)와 함께 주 버튼을 `다시 시작`(같은 AI 작업, 새 request_id)으로 바꾸고 `AI 작업은 이미 만들었습니다 — ‘다시 시작’은 같은 AI 작업을 시작하며 바꾼 입력은 반영하지 않습니다.`를 보인다. 이 상태에서는 새 AI 작업을 만들지 않는다. 성공하면 탭을 열고 `AI 작업을 만들었습니다.`(탭 상한이면 §2 안내)를 토스트로 보인다. 시작 전에 설정으로 이동하면 만든 초안을 탭에 열어 두고(`시작하지 못한 AI 작업을 탭에 열어 두었습니다…`, 탭 상한이면 목록 안내) 대화상자를 닫는다.

**base_changed 재생성**: start 거절 reason이 `base_changed`/`repository_changed`면 `다시 시작`을 막고 `현재 HEAD로 다시 만들기`(또는 `현재 저장소로 다시 만들기`)를 보인다. 누르면 입력을 그대로 두고 기존 draft를 가능하면 cancel한 뒤(실패해도 draft는 목록에 남을 뿐) 저장소를 다시 확인해 새로 만든다.

제출이 막힌 이유는 버튼 위 한 줄(`aria-describedby`)로 보인다: 팀 선택 필요 / 팀 없음 / 역할 연결 확인 중 / 이전 결과 확인 중 / 이미 만듦. 역할 부족 안내나 연결 조회 오류가 보이면 겹쳐 말하지 않는다. 모델 목록 refresh가 선택값을 바꾸지 않고, 임의 모델 대체는 금지다.

### 빠른 설정

**설정 → AI 작업** 첫 카드는 `runtime.detect` 결과다. codex/claude/opencode마다 버전·절대 경로·로그인 흔적(found/not_found/unknown)·호환 등급(`자동 실행 검증됨` / `이 PC에서 확인됨` / `같은 계열 버전은 검증됨 · 지금 확인으로 확정` / `자동 실행 미검증` / `설치되지 않음`)을 표시한다. 감지는 읽기 전용이며 저장하지 않고 인증 파일 내용을 반환하지 않는다. 검증 역할이 없거나 일부면 그 사실을 그대로 표시하고 검증됐다고 추정하지 않는다. 모델 칸은 자유 입력이고, 후보 목록은 `configured_model_id`(사용자가 CLI에 설정해 둔 모델) → `proven_model_id`(라이브 증거가 고정한 모델) → `models`(런타임이 지금 광고하는 목록) 순서로 채운다. 기본값은 `configured_model_id`이며, `proven_model_id`와 다른 값을 입력하면 힌트로 경고만 하고 동의를 요구하지 않는다. `models`는 고르기 힌트일 뿐이라 호환 등급이나 역할 판정에 쓰이지 않는다.

`이 모델로 팀 만들기`는 같은 runtime·program·provider·model·subscription·참조 없음 binding을 재사용하거나 저장 → `binding.probe` → 역할 capability 확인 → 역할 primary가 모두 그 binding인 template을 재사용하거나 저장한다. probe가 verified가 아니거나 한 역할이라도 미검증이면 template을 만들지 않고 이유를 표시한다. 미검증 버전은 daemon이 `experimental_roles`를 알려 준 경우에만 `실험적으로 사용` 체크(연결당 한 번 동의)와 위험 고지를 보이고, 동의해야 팀을 만든다. 실험적으로도 리뷰 역할을 채울 수 없으면 `빠른 모드(리뷰 생략)에서만 쓸 수 있습니다.`와 함께 리뷰 없는 팀(`{label} (리뷰 생략)`)을 만든다. 필요한 기능이 없으면 `필요한 기능이 구현되지 않아 사용할 수 없습니다.`. OpenCode는 저장된 연결 참조가 필요하므로 빠른 설정 대상이 아니며 직접 입력으로 안내한다. 기존 모델 연결 폼은 `직접 입력(고급)`으로 접고, 팀 템플릿에는 네 역할을 한 번에 채우는 `모든 역할에 같은 모델` 선택을 둔다. 검증 명령 인자는 공백 구분(따옴표 묶음) 또는 JSON 배열을 받는다. 저장된 실험적 연결은 `동의한 버전 {version}`을 보인다. CLI가 업데이트돼도 동의는 그대로 유효해 다시 동의를 요구하지 않으며, 자가 진단은 `지금 확인`으로 다시 확인한다.

Z.ai Coding Plan은 별도 CLI가 아니라 Claude Code가 서비스하는 두 번째 provider 경로이므로 `runtime.detect`에 줄이 없다. 대신 claude가 `verified`이고 program이 있을 때 Claude Code 줄에서 `Claude Code · Z.ai Coding Plan` 카드를 파생해 같은 경로·버전·등급을 그대로 쓰고 provider만 `zai-coding-plan`으로 바꾼다. 모델 후보는 Coding Plan 고유 id(`glm-5.3[1m]`, `glm-5.3-flash[1m]`) → `alt_models`가 알려 준 관측 id → 옛 daemon이 `models`에만 담아 보낸 비-Anthropic id 순서이며, 팀 템플릿의 같은 그룹도 이 목록을 쓴다. Anthropic 카드는 `claude-*`/alias만 남겨 두 경로가 서로의 id를 제안하지 않는다. 로그인 줄 자리에는 앱 전용 키 저장소의 Z.ai 키 유무(`등록됨` / `없음 — 설정 → 연동에서 등록하세요` / `확인 불가`)를 표시하고, 키가 없는 것이 확인되면 `이 모델로 팀 만들기`를 잠근다(데몬이 `zai_key_missing`으로 거절하기 전에 막는다). 키 상태는 마운트와 `다시 찾기`에서 읽고, 같은 설정 화면의 Z.ai Coding Plan 카드가 저장·삭제를 알리는 구독 갱신 이벤트에도 다시 읽어 `다시 찾기` 없이 그 자리에서 풀린다. 데스크톱 브리지가 없는 빌드는 물어볼 곳이 없으므로 `확인 불가`로 두고 막지 않는다. 출시 증거는 provider·인증 경로로 묶이므로(`capability_evidence::shipped_route_matches`) 이 카드의 호환 등급은 Claude Code 줄이 `자동 실행 검증됨`이어도 항상 `자동 실행 미검증`이다. 따라서 `실험적으로 사용` 동의를 받아야 팀을 만들고, 위험 고지는 버전 대신 경로를 지목한다(`Z.ai 경로는 출시 검증 대상이 아닙니다 …`). 팀 템플릿의 Z.ai 선택이 언제나 동의를 요구하는 것과 같은 판정이다. 저장되는 binding은 subscription·참조 없음이며 실행 시 `claude-exec --provider zai`와 같은 키 저장소를 읽는다([03 §Claude](03-adapters.md)).

같은 대화상자·설정 화면에서 빠른 설정은 capability gate를 우회하지 않는다. AI 작업 start의 역할별 capability 검사는 그대로다.

### 모델 연결의 설치 확인

**설정 → AI 작업**에 빠른 설정 → 사용법 → 모델 → 팀 → 검증 순서로 둔다. `설치 확인` 버튼 문구는 `지금 확인`이며, 저장된 모델에만 가능하고 미저장 변경이 있으면 비활성화한 채 먼저 저장하도록 안내한다. 누르면 설치 버전 조회에 이어 로컬 자가 진단을 함께 수행한다(모델 호출·인증 토큰 사용·사용자 설정 변경 없음, [11 §6](11-local-evidence.md#6-로컬-자가-진단-agent_runtimelocal_proberrs-신설)). 결과의 installation 상태를 두 언어로 표시하며 enabled로 성공을 추정하지 않는다. 실패하면 예전 버전을 제거하고, 반환된 binding과 revision을 편집 폼과 모델 목록에 함께 반영한다. 설치 확인은 인증·모델 이용 권한 검사와 구분한다.

연결마다 **신뢰 칩** 하나를 보인다: `출시 검증됨`(필수 기능이 모두 출시 증거) / `이 PC에서 확인됨`(자가 진단 또는 실행 관측이 증명, 동의 없음) / `실험적`(필수 기능 중 하나라도 동의로 열림) / `미확인`. 필수 기능은 structured_result·events·cancel과 read_only 또는 scoped_write다. 칩 아래 한 줄로 근거를 보인다: `프로토콜 확인 · sandbox 12/12 · 성공 실행 N회 · {확인 시각}`; 선택한 모델이 이 CLI의 모델 목록에 없으면(`model_listed === false`) 경고를 덧붙이되 막지 않는다([11 §8](11-local-evidence.md#8-ui-계약-05-문서-보충)).

상세의 capability_* 대기는 시도 횟수/예산을 예약하지 않았다는 안내와 설정 열기·모델 변경 동선을 제공한다. 모델 선택기를 열 때 목록을 다시 읽고(활성 + 정책 허용 연결만) 해당 할 일의 필수 기능이 없는 연결은 이유와 함께 비활성화한다. 예약 뒤 버전 변경/조회 실패는 실패 기록으로 남으며, CAPABILITY_UNSUPPORTED와 request_not_submitted 증거가 모두 있을 때만 모델에 요청을 보내지 않았다고 안내한다. 설치를 확인한 뒤 명시적으로 재시도하며 과거 Run은 보존한다.

## 4. Lead 대화와 입력

user/agent/system 메시지를 구분하고 본문은 body_ref를 다시 읽는다(8 MiB LRU, store에 원문 없음). 맨 위에는 실패·중단으로 끝난 AI 작업의 요약 카드(`AI 작업이 실패로 끝났습니다` + 원인 문장·code + `설정 열기`(실패만) / `같은 목표로 새 AI 작업`), 이어서 사용자 목표 카드와 접을 수 있는 `채택된 계획 · 할 일 N개` 카드가 온다. 계획 개수는 사용자 의미의 할 일(대체됨·검증·통합 제외)만 센다. 계획 단계에 메시지가 없으면 `Lead가 계획을 세우는 중입니다 · 경과 {시간}`, 그 밖에는 `아직 대화가 없습니다…`. 메시지의 run 링크(`▸ 활동`)는 오른쪽 할 일 상세를 연다. 매 token마다 카드/알림을 생성하지 않는다.

**결정 답변 카드**: 결정에 답한 시스템 메시지는 원문 JSON 대신 `결정: {선택지}` 카드로 보인다. 본문이 01 §8 `decision_answer` 문서(`kind`, `decision_id`, `decision_kind`, `option_id`, `option_label`, `answer_ref`, `answer_text`)이거나 기존 `{decision_id, option_id}` 부분집합이면 답변으로 읽고, 결정의 `answer_message_id` 연결도 쓴다. 라벨은 option id 번역 → 결정의 선택지 label → 문서의 option_label → id 순서, option이 없으면 `직접 입력한 답변`. 자유 입력은 공백을 접어 160자로 자른 `입력: {text}`로 덧붙인다. 다른 kind의 JSON(예: `integration_exclusion`)과 일반 텍스트는 답변이 아니다.

기본 composer 수신자는 항상 `AI 작업 전체에 요청`이다. 할 일 선택으로 수신자를 자동 변경하지 않는다. 상세의 `이 할 일에 추가 지시`는 `받는 사람: {할 일} · {모델}`이 고정된 별도 입력창을 연다. 두 입력창의 draft state를 공유하지 않는다. 자동 통합 단계에는 이 입력 대신 `자동 통합 단계입니다. 변경 지시는 Lead에게 보내세요.`를 보인다.

전송 상태는 보내는 중/대기 중/전달됨/전달 여부 확인 필요/전달 실패다. queued를 delivered로 표시하지 않는다. 조합 중 Enter 전송 금지: React composition flag와 native isComposing 둘 다 검사한다. Shift+Enter는 줄바꿈, Enter 전송은 사용자 설정(`missionEnterSend`, 기본 켜짐)을 따르고 Ctrl/Cmd+Enter는 항상 전송이다. 오류 시 draft/수신자 보존. 끊김이면 전송을 막고 `연결이 끊겨 지금은 보낼 수 없습니다. 입력한 내용은 그대로 둡니다.`를 보인다.

잠긴 입력은 상태별 이유를 보인다: 완료(`완료된 AI 작업이라… 후속 AI 작업을 만드세요.`), 실패, 중단, 멈추는 중, 보관, 그 밖에 수신자(할 일)가 끝났거나 받을 수 없음(`이 수신자는 새 지시를 받을 수 없습니다. 최신 상태를 확인하세요.`). 끝난 AI 작업의 전체 입력창은 draft와 미해결 전송이 없을 때 `이 결과로 후속 AI 작업 만들기`(완료) 또는 `같은 목표로 새 AI 작업`(실패·중단)으로 전환한다. 완료면 아래에 후속 안내를 붙인다: 확정됐으면 `새 AI 작업은 이전 확정 결과 위에서 시작합니다. 내 브랜치에 반영하려면 ‘결과 가져오기’를 사용하세요.`, 아니면 `결과를 먼저 내 브랜치로 가져와야 새 AI 작업이 그 위에서 시작합니다.` + `결과 가져오기 안내 보기`(결과 화면의 가져오기로 이동).

일반 입력창의 초안/전송 시도는 UI 세션에서 AI 작업 ID와 target task ID별로 보존한다. 화면 이동이나 상세 닫기로 전송 요청을 버리거나 새 수신자로 옮기지 않는다. 업로드 중에는 본문과 수신자를 고정하고 실제 `mission.message` 직전에 최신 상태와 revision을 검사한다. 저장 응답이 불명확하면 UUID·본문 ref·수신자·revision을 그대로 유지해 `전송 결과 다시 확인`을 제공한다. 확인된 validation/CAS 거절 후에만 새 요청을 만들며, transport/storage 오류는 거절 증거로 취급하지 않는다. 종료 상태에서도 기존 요청의 영수증 재생은 가능하다. 전송 직전에 IndexedDB의 수신자별 atomic slot에 version과 정확한 params를 저장하며 transaction 완료 전에 mutation을 보내지 않는다. 본문 원문·전체 snapshot은 이 DB에 저장하지 않는다. 앱 재시작 뒤 같은 입력창은 이 요청을 복원하고 artifact의 전체 bytes·SHA-256·UTF-8을 검사해 본문을 표시한다. 초기 복구가 끝날 때까지 입력을 잠그며 읽기 실패는 명시적 재조회로 복구한다. 성공/확인된 거절 뒤 기록 삭제가 실패하면 요청을 유지하고, 다른 창의 요청을 덮어쓰거나 삭제하지 않는다. 미전송 초안은 UI 세션에만 남는다.

사용자가 위를 읽는 동안 tail-follow를 멈추고 `새 활동 N개`를 표시하며, 위쪽 본문이 늦게 채워져도 읽던 위치를 지킨다(scroll anchor). 사용자가 펼친 카드 안의 변화는 끝으로 끌어내리지 않는다.

## 5. 할 일 목록

머리는 제목 `할 일`, 카운터 `실행 N · 완료 N · 결정 N`, 필터, 검색이다. 행 key는 task_id, 정렬은 plan ordinal이며 상태가 바뀌어도 재정렬하지 않는다. 행은 상태 글리프 + 제목 + 모델 + `시도 N`(2회 이상) + `실험적 연결` 배지(어느 시도든 필수 기능이 동의로 열린 연결로 실행했으면, `isExperimentalBinding` 기준, tooltip과 숨김 낭독 문구) + 상태 문구다. 아래 보조 줄에 이유와 동선을 둔다. 재시도는 같은 행에서 `시도 이력`을 펼친다.

| 상태 | 표시 | 보조 줄 |
|---|---|---|
| planned | ◷ 선행 할 일 대기 | `선행 N개` |
| ready | … 실행 대기 | `실행 대기 · 자원 할당을 기다립니다`, 일시정지 중이면 `일시정지됨 · 계속 실행을 기다립니다` |
| running + prepared/starting Run | ◔ 시작 중 | 3분 이상 활동 없으면 상태 확인 중 |
| running + running/awaiting_input Run | ▶ 실행 중 | `실행 중 · {경과}`, 마지막 활동 3분 이상 전이면 `마지막 활동 N분 전 · 상태 확인 중` |
| awaiting_input | ? 응답 필요 | 결정 배너로 답한다 |
| awaiting_review | ◸ 변경 확인 중 | capture/허용 범위 검사 |
| blocked | ⊘ 진행 불가 | 대기 이유(아래) |
| succeeded | ✓ 할 일 완료 | AI 작업 최종 검증과 구분 |
| failed | ✗ 실행 실패 | `남은 재시도 N회`(정책의 할 일당 시도 한도 − attempt_count) |
| cancelled | — 취소됨 | 이력 유지 |
| superseded | ↘ 계획에서 대체됨 | 이력 유지 |

**대기 이유**: 다음 행동 안내가 붙은 전용 짧은 문구를 먼저 쓴다 — capability_* `호환성 확인 필요`, provider_rate_limited `제공자 제한 대기 · 상세에서 해제 시각 확인`, transient_retry `자동 재시도 대기 · 상세에서 시각 확인`, plan_format_repair `계획 형식 수정 대기`. 그 밖은 blocked_code를 공용 이유 문구로 바꾼다(선행 할 일 실패, 이전 실행 종료 확인 중, 새 시도 선택 대기, 복구 방법 선택 대기, 통합 충돌, 활성 시간·자동 시작·시도 한도 도달, 비용 한도 초과·확인 불가·정책 대기, 필요 기능 미검증, AI가 진행 불가를 보고함, 제공자 요청 한도 대기·연결 불가, 모델 연결 없음·사용 불가, 로그인 필요, 모델 사용 불가; 모르면 `진행 불가`). `dependency_failed`는 실패·취소된 선행 할 일 이름을 링크로 붙이며 누르면 그 할 일을 선택한다. 필수 할 일 수정 계획을 맡은 Lead 행에는 `필수 할 일 수정 계획 · N차`를 붙인다.

**상태 확인 기준**: stale 판단은 live Run의 `last_activity_at ?? started_at`이 3분(STALE_ACTIVITY_MS) 넘게 지났을 때이며 실패 판정이 아니다. 경과 표시는 30초마다 갱신한다.

필터는 전체/실행 중/응답 필요/대기/완료. `응답 필요`는 열린 결정이 영향을 주는 할 일(결정 N과 같은 기준), `대기`는 planned·ready·blocked·awaiting_review, `완료`는 succeeded·failed·cancelled·superseded다. 검색은 title/역할(slug·표시 이름)/model. `실행 N`은 live Run(prepared/starting/running/awaiting_input/stopping) 수, `완료 N`은 succeeded Task 수, `결정 N`은 open Decision 수다. 예상 완료 시간/근거 없는 진행 퍼센트는 생성하지 않는다. 결과가 없으면 `표시할 할 일이 없습니다.`.

12행까지 보이고 넘으면 `더보기`로 12행씩 늘린다(필터·검색을 바꾸면 초기화). 목록은 button 행의 list이며 ArrowUp/Down으로 선택과 focus를 옮기고 Enter로 선택, Escape로 중간 폭 side sheet를 닫는다. 색 외 글리프/문구로 상태를 표현한다. 좁은 목록(≤320px)은 제목을 첫 줄, 모델·상태를 둘째 줄에 둔다.

## 6. 상세와 분할

header는 할 일 제목 · 상태 문구 · `실험적 연결` 배지, 메타(역할 / 모델(없으면 `없음`) / `시도 N/한도`와 실행 상태 / `저장된 실행 시간`과 ⓘ 시간 기록 방식)다. 통합 할 일은 `충돌 해결(Integrator) 모델: {label · model}`을 보인다. 그 아래 **상태 안내**와 **제어**, **추가 지시**가 온다.

**Notice 한 줄 형식**(StatusNotice): 한 줄 상태 + 행동 버튼 + `자세히` 접기. 긴 설명은 접힌 곳에만 두고 낭독 영역을 만들지 않는다. 안내 종류는 제공자 요청 한도(`제공자 요청 한도 대기 · 해제 {시각}` + `모델 변경`), 자동 재시도(`자동 재시도 대기 · {시각} 이후` + `모델 변경`), 계획 형식 수정(`계획 형식 수정 대기` / `계획 자동 수정 중단 · 결정 필요`), 필수 할 일 수정 계획(`필수 할 일 수정 계획 진행 중 · N/M차` / `Lead 수정 계획 실패 · N/M차`), 결과 불명 실행(`이전 실행 종료 확인 중 · 새 시도 대기` / `실행 종료 확인 · 새 시도 여부 선택`, observed tree면 `관찰 밖 자식 프로세스가 남아 있을 수 있음`), 필요 기능(`필요 기능 미검증으로 대기` / `실행 전 호환성 확인 실패 · 모델에 보내지 않음` + `설정 열기`·`모델 변경`)이다. 전용 안내가 있는 blocked code는 `대기 이유:` 줄을 중복해 보이지 않는다. provider_blocked는 `대기 이유`와 펼친 `AI 보고` 본문을 보인다.

**사용자 확인 정리**(`mission.run.attest_exited`): 종료 증거가 없어 실행 자리를 차지하는 unknown/interrupted 실행에는 notice `종료 증거가 없어 이 실행이 실행 자리를 계속 차지하고 있습니다.` + `프로세스 종료를 직접 확인했습니다`를 둔다. 누르면 확인 방법(같은 실행의 exec 기록일 때만 PID·프로세스 그룹, macOS·Linux `ps -p <pid> -o pid,lstart,command` 또는 활동 모니터, Windows 작업 관리자), 체크박스 `해당 프로세스가 더 이상 실행 중이 아님을 확인했습니다`, 고지 `제공자 결과와 외부 영향은 확인되지 않은 상태로 남습니다.`를 펼친다. 체크해야 `직접 확인으로 정리`를 보낼 수 있다(mutateWithResync, 최신 store에서 이미 정리됐으면 보내지 않음). 거절(`attestation_not_applicable`)은 다시 동기화 동선의 오류로 보인다. 같은 실행의 exec 기록이 데몬이 되찾아 감시할 수 있는 그룹 신원(신원·시작 시각·그룹 참조 + cgroup v2/`cgroup` 또는 macOS guardian/`observed_tree`, 데몬 `has_recoverable_group`과 같은 조건)을 가지면 버튼 대신 `데몬이 이 실행의 프로세스 그룹을 다시 찾아 감시할 수 있어 종료 확인을 기다립니다.`(+자세히)만 보이고 전송 직전에도 같은 조건으로 보내지 않는다. 정리된 실행은 결과 불명 안내 대신 `직접 확인으로 정리됨 · 외부 영향 미확인`(+자세히)으로 구분하고, 결과 화면 확인 항목에도 같은 라벨을 붙인다.

**제어와 비활성 사유**: 끝나지 않은 할 일은 `이 할 일 실행 중단`(live Run이 있을 때) 또는 `할 일 취소`, 실패·취소면 `다시 시도`, 그리고 `모델 변경`(배정만 바꿀 수 있는 상태: planned·ready, capability·비용·요청 한도·자동 재시도·계획 형식 수정·새 시도 선택 대기, 통합 충돌 중 Integrator 배정) 또는 `모델 변경 후 재시도`(그 밖)를 둔다. 통합 자동 단계는 충돌 결정이 열려 있을 때만 모델 변경을 보인다. 비활성 버튼은 아래 한 줄로 이유를 보이며 같은 이유는 한 번만 보인다: `이전 실행의 종료를 확인하는 중입니다.` / `실행 중에는 바꿀 수 없습니다. 먼저 실행을 멈추세요.` / `AI 작업이 실행 중이거나 일시정지일 때만 가능합니다.` / `Lead가 이 할 일의 수정 계획을 맡고 있습니다.` / `먼저 통합 충돌 결정에 답하세요.` / `검증 할 일은 모델을 사용하지 않습니다.` / `실패했거나 아직 시작 전인 할 일만 모델을 바꿀 수 있습니다.` / `이미 다음 단계로 진행했습니다.` + `Lead 대화에서 대체 계획 요청` 링크(Lead 입력창으로 이동·포커스). 완료·대체된 할 일은 이유를 보이지 않는다. 모델 선택기는 고르면 확인 없이 바로 요청한다(retry는 모델 변경과 재시도 승인을 한 CAS로, reassign은 배정만). 실험적 연결 동의는 CLI 업데이트로 만료되지 않으므로 이 이유로는 비활성화하지 않는다. 취소·다시 시도·모델 변경은 누른 순간(취소는 확인창을 연 순간, 모델 선택기는 연 순간)의 할 일 상태·배정·붙잡은 실행·시도 수를 기억하고, 전송과 REVISION_CONFLICT 뒤 재전송 모두 그 전제가 그대로일 때만 보낸다 — 다르면 보내지 않고 `화면 정보가 바뀌어 요청을 보내지 않았습니다…`로 알린다.

탭은 `활동` / `실행`(조건부) / `변경` / `검증`(tablist, ArrowLeft/Right 순환).

- **활동**: `mission.activity`를 offset으로 읽어(한 번에 최대 4페이지, 1초 주기, 완료되면 중지) 마지막 200줄·256 KiB를 보인다. 새 출력은 사용자가 맨 아래(24px 이내)를 보고 있을 때만 따라가고, 위로 올리면 멈추고 `최신으로`를 보인다. 실행이 없으면 `아직 시작된 실행이 없습니다.`, 실패하면 `활동을 가져오지 못했습니다.` + `활동 새로고침`. raw protocol은 개발 진단에만 둔다.
- **실행**: run의 binding snapshot이 `native_terminal_attach.supported`일 때만 탭을 보인다. 현재는 terminal을 붙이지 않고 `이 실행은 터미널 화면을 연결할 수 없습니다…`, `터미널 화면 없음 — 활동 기록만 볼 수 있습니다`, `활동 뷰어 열기`를 보인다. 가짜 terminal 금지.
- **변경**: 결과가 있으면 탭 이름을 `전체 결과 변경`으로 바꾸고 `저장된 변경 · 파일 N개`, 이 할 일의 실행이 결과에 포함됐는지, `이 할 일 범위의 파일`(contract.allowed_paths) → `그 밖의 파일`을 보인다. 결과 전이면 구현·통합 단계는 `진행 중 변경`, 그 밖은 `변경 없음`.
- **검증**: 결과의 검증이 있으면 `전체 검증`으로 바꾸고 `이 할 일 관련 검증`(이 할 일 또는 같은 requirement) → `그 밖의 검증`을 보인다. 각 행은 결과 문구와 별개로 입력 무결성(`입력 쓰기 차단 보장` / `미보장(관찰만)` / `알 수 없음`)과 종료 코드를 붙인다.

할 일 클릭은 상세 교체다. agent-view 탭은 같은 run 관찰이며 새 실행이 아니다. native attach를 연결할 때는 다음을 지킨다: 같은 PTY의 여러 view는 기존 입력 소유권을 따르고(최초 view는 reader, 사용자가 `입력 제어 가져오기`를 요청), UI 입력과 orchestrator 자동 입력을 동시에 보내지 않으며, 조건을 만족하지 못하면 read-only 관찰만 지원한다. terminal view는 lazy acquire하고 숨김 cache는 전체 4개 LRU(eviction은 detach/dispose만, run 종료 금지), 재표시는 journal replay 상태를 표시한다. 기존 일반 terminal cache 정책은 변경하지 않는다.

## 8. 질문과 제어

**결정 패널 형식**(DecisionPanel, `max-height: 50vh` 스크롤): header `결정 필요` + `진행 중단됨`(blocking) / `답변됨` → **상황 1문장** → 판단 자료(실패 메시지 첫 줄, 제공자 한도 해제 시각, 로그인 방법 보기·설정 열기·모델 변경 동선, AI 보고, 관찰 범위 안내, 파일 변경, 충돌 파일, 제안된 할 일(역할·선택·선행) 과 대체되는 할 일, `영향받는 할 일 N개`와 제목 링크, 자유 입력) → **선택지 footer**(스크롤 영역 안 sticky; 버튼마다 아래 `누르면 생기는 일` 1줄, `aria-describedby`) → `자세히`(긴 경고·설명, 보고 코드·메시지, 비용 예약 설명, Lead의 설명, 원문). 상황 문장은 질문 원문 대신 종류별로 만든다: 파일 변경 허용, 통합 충돌, 리뷰 자동 수정 한도, 비용 대기, 활성 시간/자동 시작 한도, 결과 불명 실행(`‘{할 일}’의 이전 실행은 끝났지만 결과가 불명확합니다 · 시도 N/M`, 통합이면 통합 실행), 실패(`‘{할 일}’ 실행이 실패했습니다 · {이유} · 시도 N/M`), AI 진행 불가 보고(`AI가 ‘{할 일}’을(를) 진행할 수 없다고 보고했습니다 · 시도 N/M`), 계획(`Lead가 할 일 N개로 된 계획을 제안했습니다.`), 보내지 않은 실행, 보냈을 수 있는 실행. 그 밖은 질문 본문.

**option id**: 선택지 라벨과 효과는 id로 번역한다 — `apply` 계획 적용, `revise` 계획 수정 요청, `accept` 허용, `decline` 거절, `resume_unsent` 보내지 않은 실행 시작, `stop_mission` AI 작업 중단(통합 충돌에서는 같은 라벨), `retry_with_instruction` 지시 추가 후 다시 시도, `change_model` 모델 변경, `replan` 대체 계획 요청, `adjust_limits` 한도 조정, `retry_failed_task` 원인 해결 후 다시 시도, `stop_failed_mission` AI 작업 중단(실패로 기록), `retry_reconciled_task` 이전 영향 확인 후 새 시도 시작(통합이면 `격리된 결과 보존하고 통합 다시 구성`), `stop_reconciled_mission` AI 작업 중단, `resolve_and_reintegrate` Integrator에게 해결 요청, `exclude_candidate` 충돌한 변경 제외 후 Lead 재계획, `stop_review_repair`·`stop_cost_mission` AI 작업 중단. 모르는 id는 daemon/모델이 준 label과 `이 답을 AI에게 전달합니다.`.

**자유 입력**: 선택지가 없으면 `답변`(+`답변 보내기`, 비었으면 `내용을 입력해야 보낼 수 있습니다.`), `retry_with_instruction`/`change_model`/`replan`이 있으면 `추가 지시`, `revise`가 있으면 `수정 요청 내용(선택)`. 조합 중 Enter는 무시하고 Ctrl/Cmd+Enter로 보낸다(일반 Enter는 줄바꿈). 본문은 UTF-8 64 KiB 이하만 보내고 넘으면 관련 버튼을 막는다. 본문은 artifact로 한 번 올린 뒤 `mission.decision.answer(option_id, answer_ref)`로 보내며 CAS 재시도는 같은 artifact를 가리킨다. 성공은 `답변됨`으로만 표시하고 저장·전달을 과장하지 않는다.

**동작 규칙**: `change_model`은 먼저 모델 선택기에서 `task.control reassign`으로 다른 연결을 지정한 뒤 답한다(그대로면 `model_not_changed`). `adjust_limits`는 답하지 않고 **한도 편집기**를 연다. 한도·비용·리뷰 수정 결정에 `adjust_limits` 선택지가 없으면 `AI 작업 한도 조정` 버튼(효과 `한도를 늘려 저장하면 실행을 이어 갑니다.`)을 추가한다. 실패 결정은 실패 code가 모델로 풀 수 있는 종류(MODEL_UNAVAILABLE, CAPABILITY_UNSUPPORTED, PROVIDER_RATE_LIMITED)면 `모델 변경`, AUTH_REQUIRED면 `로그인 방법 보기`·`설정 열기`를 둔다. 파일 변경 승인은 완전한 변경 목록이 없으면 `허용`을 막는다. obsolete 질문은 버튼 disabled + `이 질문은 이미 처리되었습니다.` + `현재 질문 열기`. 오류는 MissionErrorNotice(다시 동기화·설정 열기·다시 시도·모델 변경)로 footer에 둔다.

**한도 편집기**(PolicyLimitsEditor; 결정 패널과 `실행 제어 → AI 작업 한도…` 팝오버가 같이 쓴다): 활성 시간(분/시간 단위 전환), 자동 시작 수, 수정 사이클(0 허용), 할 일당 시도, 병렬 실행 수, 비용 상한과 미확인 비용 처리. 각 행에 `최대 {ceiling}`과 `사용 {used} / 한도 {limit}`(병렬은 `실행 중`, 비용은 `보고 · 예약·추정`)을 보인다. 정수가 아니면 `한도는 정수로 입력하세요.`, 범위를 벗어나면 blur 때 ceiling(defaults.json) 안으로 맞추고 `허용 범위를 벗어난 값은 범위 안으로 맞췄습니다.`. 저장은 `mission.policy.update` + mutateWithResync로 사용자가 건드린 필드만 최신 정책 위에 덮어쓴다. 실행 중·일시정지·초안에서만 편집하며 저장하면 `저장했습니다. 다음 예약 검사부터 새 한도를 적용합니다.`. `자세히`에 활성 시간 정의와 비용 예약 설명을 둔다.

**팀 편집기**(MissionTeamEditor; `실행 제어 → 팀 바꾸기…` 팝오버): 작업 정책이 허용한 역할(`policy.allowed_roles`)마다 활성 모델 연결을 고른다. lead·builder와, 독립 리뷰가 켜져 있으면 reviewer는 비울 수 없고(데몬 policy.update와 같은 규칙) integrator 같은 선택 역할은 `맡기지 않음`으로 뺀다. 역할이 맡는 할 일 종류를 지원하지 않는 연결은 비활성 선택지 + 이유로 보이며 임의 대체는 없다(05 §3). 사라졌거나 꺼진 연결이 배정돼 있으면 `지금은 없는 연결 — 다시 고르세요`로 다시 고르게 한다. 저장은 `mission.policy.update` + mutateWithResync이며 고른 연결을 `allowed_binding_ids`에 합집합으로 더하기만 한다 — 실행 중인 Run이 쓰는 연결을 빼면 데몬이 거절하기 때문이다. 활성이 아닌 fallback은 저장할 때 떨군다(데몬은 primary·fallback 모두 활성을 요구). 초안·실행 중·일시정지에서만 편집하며, 저장하면 `저장했습니다. 다음 배정부터 새 팀을 씁니다.` — 이미 보낸 할 일의 모델은 그대로다.

Codex 파일 변경 승인은 일치하는 실행 요청에 연결된 파일 경로·추가/수정/삭제·이동 경로·diff를 escaped text로 보여 주고 추가 root 쓰기 권한은 별도로 경고한다. 질문 배너와 상세에는 내부 provider request ID 대신 사용자용 질문을 표시한다. 저장된 답변이 실제 provider에 전달됐는지는 기존 outbox 상태로 구분한다.

| UI 행동 | 실제 동작 |
|---|---|
| 새 실행 일시정지 | control(pause); 현재 run이 끝날 때 pausing→paused |
| 계속 실행 | control(resume); ready scheduling |
| AI 작업 중단 | 확인창(`지금 {live Run}개 실행이 종료되고…되돌릴 수 없습니다`) 후 control(cancel); stopping→종료 확인 후 cancelled |
| 이 할 일 실행 중단 / 할 일 취소 | 확인창(의존 할 일 수, 필수면 완료 조건 유지 안내) 후 task.control(cancel) |
| 다시 시도 | task.control(retry); 새 Run/attempt |
| 모델 변경 / 모델 변경 후 재시도 | task.control(reassign / retry + binding_id); 확인 없이 바로 요청 |
| 질문 답변 | decision.answer; 저장됨/전달됨 구분 |
| 프로세스 종료를 직접 확인했습니다 | mission.run.attest_exited(체크 후) |
| 이 결과 확정 | 확인창 후 accept; 정확한 candidate와 확인 목록 |
| 이 결과 버리기 | cancel(가능하면) → 종료 확인 → archive |
| 작업 공간 정리 | 확인창 후 workspace.cleanup |
| AI 작업 탭 닫기 | 로컬 hidden=true; 실행 계속, 안내 토스트 |
| 보관 / 되돌리기 / 보관 해제 | 끝난 AI 작업만 archive; unarchive; 파일 삭제 없음 |

전체 중단은 한 번 확인하고 worker마다 반복 질문하지 않는다. 중단·보관 오류의 `다시 시도`는 확인창부터 다시 받는다. 결정 배너는 질문과 영향받는 할 일을 연다. 다른 탭에서는 badge만 갱신하고 강제 전환/모달 금지. product 질문과 tool approval을 분리한다.

충돌 결정의 **충돌한 변경 제외 후 Lead 재계획**에는 `자세히`에 의존 결과도 제외됨, 이전 파일·기록 보존, 필수 할 일의 대체 계획, 새 결과의 재검증·리뷰를 안내한다. 답변 후 Planning 단계와 새 Lead 할 일을 표시하며 실패한 통합 Run을 성공으로 바꾸지 않는다. 기존 실패 통합 Task는 superseded다. 같은 결정의 중복 제출은 기존 요청 결과를 사용한다.

### 할 일 취소와 완료 조건

필수 할 일의 취소 확인과 취소 후 상세에 `필수 할 일을 취소해도 완료 조건은 그대로입니다…`를 표시한다. 종료 확인 후 같은 단계에서 명시적 재시도 또는 허용 모델 변경 후 재시도를 제공한다. 미종료 실행과 이미 지나간 단계의 재시도는 비활성화하며 Lead 대화의 대체 계획 동선을 안내한다. 취소한 필수 할 일은 확정을 막고, 원래 Run을 성공으로 표시하거나 요구사항을 삭제하지 않는다.

## 9. 결과 화면

결과가 없으면 `아직 확인할 결과가 없습니다.`만 보인다. 결과가 있으면 **위쪽 요약(고정)** 과 **아래 상세(스크롤)** 로 나눈다.

**요약**: `결과` + 상태(`확정됨` / 실행 중이 아니면 AI 작업 상태 / `{단계} · 아직 확정 단계가 아닙니다` / `검증 완료 · 확정 대기` / `확인 필요 · 확정 대기`) → 결과가 바뀌었으면 `확인하는 동안 결과가 바뀌었습니다…` + `갱신` → 실험적 연결 경고 → **확정 체크리스트**(확정 전) 또는 `확정했습니다. 원래 브랜치는 그대로입니다 — 아래 방법으로 결과를 가져오세요.` + 작업 공간 정리 제안(확정 후) → `이 결과 확정` + 첫 미충족 이유 → 확인창 → `수정 요청` / `이 결과 버리기` → 결과 가져오기 요약.

**확정 체크리스트**는 daemon `acceptance_ready`(workflow.rs)와 `apply_accept` 사전 검사의 화면 사본이다. 화면은 모든 미충족 항목을 daemon 순서대로 모으고 `issues[0]`을 버튼 옆 이유로 쓴다. 행은 적용되는 범주만 고정 순서로 보인다: `확정 대기 단계` · `필수 할 일 완료` · `요구사항 검증이 현재 결과에서 통과`(요구 명령이 있을 때) · `검증 입력 쓰기 차단 보장`(require_enforced_verification) · `현재 결과의 독립 리뷰 완료`(require_independent_review) · `차단·주요 지적 없음` · `직접 확인 완료`(확인 대상이 있을 때) · `실행 중이거나 결과가 불명확한 실행 없음` · `답하지 않은 차단 결정 없음`. 각 행은 ✓/✗ 글리프 + 숨김 `충족/미충족`, 항목별 이슈 최대 5개와 `외 N건`, 이슈 링크(`할 일 보기` / `요구사항 보기` / `검증 보기` / `확인 항목으로` / `지적 보기` / `결정 보기`, 상세의 data-anchor로 스크롤·focus)를 둔다. 필수 기능이 동의로 열린 연결(`isExperimentalBinding`)로 실행한 할 일이 있으면 정보 행 `실험적 연결로 실행한 할 일 N개 · 확정을 막지는 않지만…`(확정 조건 아님)을 덧붙인다. 확정 버튼은 phase가 awaiting_acceptance이고 모든 조건을 채웠을 때만 연다(daemon은 phase를 보지 않음).

**확정 binding**: 버튼은 화면이 확인하기 시작한 candidate에 묶는다. 후보가 바뀌면 disable + 갱신 요구, 확인 체크는 모두 초기화한다. 확인창(`결과 확정`, `검증 N건과 직접 확인 M건을 기록하고…원래 브랜치에는 자동으로 반영되지 않습니다.`)의 전송은 최신 snapshot에서 같은 후보·같은 확인 대상일 때만 `mission.accept(candidate_id, acknowledged_verification_ids, human_requirement_ids, acknowledged_reconciled_run_ids?)`를 보낸다. O1은 publish 없이 완료되므로 `배포 완료`, `main 반영 완료` 문구 금지.

**직접 확인 체크**(`직접 확인할 항목`, 확정 전): 사용자 확인 요구사항(`직접 확인했습니다: {요구사항}`), observed 검증(`‘{명령}’ 검증은 입력 쓰기 차단이 보장되지 않은 채 통과했습니다. 이 한계를 확인했습니다.`), 과거 Unknown/Interrupted 실행(설명 `과거 실행의 제공자 결과와 외부 영향은 알 수 없습니다…` + 실행별 `‘{할 일}’ 시도 N({상태})의 이전 변경과 외부 영향을 확인했습니다.`, 사용자 확인 정리 라벨, `상세 보기`)을 체크한다. 기본값은 미확인이다. 종료 증거가 없는 실행은 체크할 수 없고 `종료 증거가 없어 아직 체크할 수 없습니다…`를 보인다. 실행 확인 키는 `run.id:reconciliation_ref.sha256`이라 증거 hash가 바뀌면 이전 확인을 재사용하지 않는다. 모두 명시적으로 확인한 ID만 보낸다. 서버는 종료·복구 결정·새 실행의 완료와 후보 출처를 검증하므로 checkbox 자체를 종료나 성공 증거로 취급하지 않는다.

**상세 순서**: (확정 후에는 결과 가져오기가 맨 위) → 직접 확인할 항목 → 요구사항 충족표(명령별로 현재 결과에서 통과 1건 이상이면 ✓, `통과 기록 없음`, `현재 결과에서 실행 안 됨`, `검증 명령 없음`, `사용자 확인 필요`) → 변경(`파일 N개 변경 · 커밋 {10자}`, 파일별 추가/수정/삭제·크기, 상한 이후 `외 N개 파일`) → 검증/입력 무결성 → 리뷰 지적(심각도, 사유 저장 후 지적 해제) → 남은 한계(열린 지적) → 결과 가져오기 → 실행 이력/사용량(제공자 보고액, 예약·추정, 미확인 실행 수).

**검증 로그**: 검증 행마다 `로그 보기({size})` details를 두고 펼칠 때만 읽는다. 큰 로그는 앞·뒤 발췌만 보이고 `로그 {size} 중 앞 {head}와 뒤 {tail}만 표시합니다.`와 `… 중간 생략 …`을 넣는다. 읽기 실패는 `로그를 읽지 못했습니다.`.

**결과 가져오기**: daemon은 사용자 브랜치를 움직이지 않으며 화면은 복사 가능한 명령만 준다. 후보 커밋은 `refs/iyagi/missions/<mission>/candidates/<candidate>`에 고정된다. `repository.inspect`로 현재 HEAD를 읽어 base면 `현재 브랜치에 병합(ff-only)` `git merge --ff-only <commit>`을, 그 밖에는 `새 브랜치로 가져오기` `git switch -c ai/<slug> <commit>`을 추천한다(slug는 제목의 영문·숫자, 없으면 `mission-<id 8자>`). `변경 보기`는 `git diff <base> <commit>`. HEAD가 움직였으면 `현재 브랜치가 AI 작업 시작 시점과 다릅니다…`, 이미 반영됐으면 `현재 브랜치에 이미 이 결과가 반영되어 있습니다.`, 확인 실패면 `현재 브랜치를 확인하지 못했습니다…`, 변경이 없으면(commit == base) 명령 대신 `변경이 없는 결과입니다…`. 요약에는 커밋과 추천 명령 복사, 상세에는 커밋·시작 커밋(base)·참조의 전체 값과 복사, 명령 선택, `터미널에서 열기`(저장소 경로로 새 terminal 탭을 열고 명령을 클립보드에 복사, 자동 실행 없음)를 둔다. 복사 결과는 2.5초 `복사했습니다`/`복사하지 못했습니다…`.

**수정 요청·버리기**: `수정 요청`(draft·running·pausing·paused)은 Lead 입력창으로 이동·포커스한다(좁은 폭은 대화 영역으로). `이 결과 버리기`(확정 전, 보관 전)는 확인창(`AI 작업을 중단하고 보관합니다. 파일과 작업 공간은 삭제하지 않습니다.`) 후 가능하면 cancel → 종료 확인 대기(`중단 중입니다. 종료가 확인되면 보관합니다.`) → archive → 되돌리기 토스트(§2)다. 이미 누가 중단했으면 이어서 종료를 기다린다.

**작업 공간 정리 제안**(daemon 계약 D `workspace.usage`/`workspace.cleanup`, 자동 삭제 없음): 확정 뒤 결과 화면은 정리 가능할 때만 `작업 공간 {size} 정리`를, 목록 행은 `작업 공간 정리 ({size})` 또는 막힌 이유(`진행 중인 AI 작업이라 정리할 수 없음` / `종료가 확인되지 않은 실행이 있어 정리할 수 없음` / `지금은 정리할 수 없음` · 크기)를 보인다. 확인창은 `이 AI 작업의 복사본 폴더와 임시 기록을 지웁니다. 확정된 결과 커밋은 남아 계속 가져올 수 있습니다. 원래 저장소는 건드리지 않습니다.`이며, 결과는 `작업 공간 N개를 지워 {size}를 확보했습니다.`와 `남긴 항목 N개`(경로 · 이유)다. 크기는 1024 단위 소수 한 자리. 사용량 조회 실패는 조용히 숨기고, 정리 실패의 `다시 시도`는 확인창부터 다시 받는다.

## 10. 연결과 닫기

daemon 연결 단절(transport의 control/data 중 하나라도 죽음) 시 마지막 snapshot은 흐리게 유지하고 `연결 끊김 · 실행 상태 미확인`(`role=alert`)을 보이며, 변경 요청 영역(실행 상세·결과)을 `fieldset disabled`로 한꺼번에 막는다(읽기는 그대로). 결정 패널은 그리지 않고 배너 `열기`와 header 제어도 막는다. Task를 failed로 변경하지 않는다. `transportStatus`가 없는 client(mock·시험)는 상태를 모르므로 끊김으로 표시하지 않는다. 끊김→연결 또는 연결 세대가 바뀌면 재연결로 보고 snapshot을 강제로 다시 뽑는다(끊김 중 시작한 동기화에 합류해 실패했으면 한 번 더). 선택/draft를 보존하고 사라진 할 일의 입력 대상을 임의 첫 행으로 바꾸지 않는다.

동기화 오류는 끊김과 구분한다: 기록 없음(`AI 작업 기록을 찾을 수 없습니다` + `탭 닫기`), 일시 오류(BUSY·timeout·SNAPSHOT_EXPIRED: `동기화 지연` + `다시 시도`, 이때 연결 상태를 즉시 한 번 확인하되 3초 주기 확인보다 자주 부르지 않는다), 그 밖의 실패(MissionErrorNotice: 원인 문장 + 처리 가능한 행동만 버튼 + `자세히`에 원문 code: message). 첫 로딩은 `AI 작업 상태를 가져오는 중…`. 힌트로 dirty인 채 동기화가 실패하면 곧바로 다시 뽑지 않고 1초 → 2초 → 4초 … 최대 30초 간격으로 다시 시도하며, 성공하면 간격을 처음으로 되돌린다. 설정·배치 편집 화면에서 목록·알림·후속 작업·되돌리기로 AI 작업(또는 agent-view) 탭을 열면 탭 화면으로 돌아온다.

앱 창 닫기는 daemon 실행 유지 정책을 따른다. quit dialog 활성 수에 O1 Exec를 포함하고 이중 계산하지 않는다. 사용자가 daemon 전체 종료를 선택하면 terminal과 AI 작업 모두 정리한다. close all tabs는 AI 작업 탭을 숨기고 일반 terminal에는 기존 종료 확인을 적용한다.

빈 상태를 아직 계획 없음/계획 중/시작 전/선택 없음(`선택한 실행이 없습니다. 목록에서 할 일을 선택하세요.`)/변경 없음/로그 만료로 구분한다. 오류는 toast뿐 아니라 관련 영역에 원인과 다음 행동을 지속 표시한다.
